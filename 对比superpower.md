⏺ 异同分析                                                                                                                  
                                                                                                                            
  核心定位对比                                                                                                              
                                                                                                                            
  ┌──────────┬─────────────────────────────────────┬─────────────────────────────────────────┐                              
  │   维度   │           autopilot (OMC)           │       brainstorming (superpowers)       │                              
  ├──────────┼─────────────────────────────────────┼─────────────────────────────────────────┤                              
  │ 目标     │ 从想法到可运行代码的全自动执行      │ 从想法到经用户认可的设计文档            │                              
  ├──────────┼─────────────────────────────────────┼─────────────────────────────────────────┤
  │ 自主度   │ 高度自主，尽量减少打扰              │ 协作式，每步需用户参与和确认            │
  ├──────────┼─────────────────────────────────────┼─────────────────────────────────────────┤
  │ 输出物   │ 可运行的代码 + 清理后的状态         │ 设计文档（spec） + 移交给 writing-plans │
  ├──────────┼─────────────────────────────────────┼─────────────────────────────────────────┤
  │ 触发时机 │ 用户明确说"build me"、"autopilot"等 │ 任何创意/功能/实现工作之前强制触发      │
  └──────────┴─────────────────────────────────────┴─────────────────────────────────────────┘                              
   
  ---                                                                                                                       
  相同点                                   

  1. 都是前置工作流：都在真正写代码之前介入
  2. 都有阶段性结构：autopilot 有 Phase 0-5，brainstorming 有 9 步 checklist
  3. 都支持 deep-interview 集成：当需求模糊时，两者都可对接 deep-interview 做 Socratic 澄清
  4. 都强调 YAGNI：避免过度设计
  5. 都有停止/升级条件：遇到根本性问题时停下来报告人类

  ---
  核心差异

  1. 人机协作程度
  - brainstorming：强制 HARD-GATE，每步都要人确认，"一次一个问题"
  - autopilot：设计为无人值守，用户"hands-off"，出错才停下

  2. 终态不同
  - brainstorming → 输出 spec 文档 → 转交 writing-plans（不写代码）
  - autopilot → 输出可运行的代码 + 通过 QA + 多维验证

  3. 适用场景
  - brainstorming：需求不清晰、需要探索方案、需要用户参与设计决策
  - autopilot：需求相对明确、用户希望全权交给 AI 执行

  4. 层次关系
  两者可以串联：brainstorming → writing-plans → autopilot（autopilot 检测到 ralplan 计划时直接跳过 Phase 0+1 进入执行）

  ---
  一句话总结

  - brainstorming = 人机共创设计，重在对齐
  - autopilot = AI 全自动交付，重在执行




  两者定位不同，不是非此即彼，而是互补的关系：

  如何选择                                                                                                                  
                                                                                                                            
  只用 superpowers（轻量）                                                                                                  
                                                                                                                            
  适合场景：                                               
  - 独立开发者，希望 Claude 遵循严格的工作流纪律（TDD、brainstorm-before-code、code review）                                
  - 不需要多模型协作（Codex/Gemini）                                                                                        
  - 不需要自主执行（autopilot/ralph/team）                                                                                  
  - 偏好人在回路，每步都要确认            

  核心价值：14 个精心调教的流程约束技能，防止 AI 乱写代码                                                                   
   
  ---                                                                                                                       
  只用 oh-my-claudecode（全功能）                          
                                                       
  适合场景：
  - 需要全自动执行（autopilot、ralph、ultrawork）
  - 需要多智能体协作（team、ccg）
  - 需要状态持久化、会话恢复
  - 需要 agent 目录（architect/executor/verifier 等专职代理）

  核心价值：38+ 技能 + 19 个专职代理，完整的多智能体编排框架

  ---
  建议

  如果你是个人开发者，不需要多模型，superpowers 足够且更克制。
  如果你需要自主执行复杂任务，选 OMC 或两者并用。
  两者都用时，superpowers 的流程技能优先（brainstorm → plan），OMC 的执行技能收尾（autopilot → team）
